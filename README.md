ゲームセンターのメダルプッシャー機を three.js + Rapier でブラウザ上に再現した作品です。プッシャーの基本ループに、モニター上のすごろく盤面と、抽選ボウル・チンチロを連鎖させています。抽選は乱数でボールや出目を誘導せず、衝突・摩擦・重力だけで結果が決まります。テクスチャも効果音も外部アセットを使わず、すべてコードで生成しています。

## 連鎖するゲームループ

メダル投入 → プッシャーが押し出す → 落ちたメダルが払い出される、という基本ループの上に 3 つの抽選ステージを載せました。メダルを 40 枚入れるごとにダイス（ミニキューブ）がホッパーから出て、それを前縁から落とすとすごろくが 1 手進みます。GOLD MINE（50 マス目）に着けば抽選ボウルへ、その結果は賭け金としてそのままチンチロに載ります。

当初はスロット + 円盤チャレンジ + JP チャレンジという構成でしたが、遊びの中心が「メダルを押す」から離れてしまったため、盤面をモニターに置いて 1 手ぶんの前進をメダルで買う形に作り直しました。

### ① メダル投入とプッシャー

投入したメダルは放物線を描いて奥のデッキに着地し、60Hz 固定タイムステップで往復するプッシャーに押される。投げ上げ初速は重力から逆算しているので、重力を変えても飛距離が崩れない

![メダルを連続投入してプッシャーが押し出す様子](docs/portfolio/gameplay-poster.webp)

*連続投入中。最大 500 枚が同時に転がっても InstancedMesh 2 枚のまま*

### ② すごろく（奥のモニター）

左のトレイで実物理のサイコロを振り、出た目そのままコマが進む。GOLD MINE まで 50 マスの一本道で、メダルマス・JP アップマス・ダイス勝負マス・特殊マスが並ぶ。全ての段を左→右に固定し、段のあいだは S 字の連絡路でつないで「どっちが前か」を読み直さずに済むようにした

![サイコロを振ってモニター上のコマが進む様子](docs/portfolio/sugoroku-poster.webp)

*1 手ぶんカメラがモニターに寄る。サイコロは演出ではなく実物理で転がしている*

### ③ 抽選ボウル（JPC）

筐体右側の台形壁の外面に直付けした漏斗状のボウル。ボールは外周を回りながら少しずつ内側へ落ち、中央の穴へ吸い込まれる。左のルーレットは回り続けていて、ボールが消えた瞬間に指していたマス目が当たり。1/16 の JACKPOT を引けば累積ジャックポット全額

![漏斗状のボウルをボールが回りながら落ちていく様子](docs/portfolio/bowl-poster.webp)

*結果は仕込んでいない。物理が決めるのは「いつ落ちるか」だけで、その「いつ」が結果を決める*

### ④ チンチロ（獲得メダル増加チャレンジ）

ボウルの結果はそのまま払い出されず、賭け金としてチンチロに載る。トレイに実物理のサイコロを 3 個投げ、役で倍率が決まる。目なしは 3 投まで振り直し、平均倍率は約 ×1.5。だからボウルの配当表そのものは低めに置いてある

![トレイに 3 個のサイコロを投げて役を決める様子](docs/portfolio/chinchiro-poster.webp)

*ピンゾロ ×5 / ゾロ目 ×3 / シゴロ ×2.5、ヒフミだけは ×0.5 で減る*

## 「結果を仕込まない」抽選設計

抽選も演出も、できる限り実物理で行いました。乱数が入っているのは盤面のマス構成とジャックポットの積立側（Economy.ts）だけです。

### 抽選ボウル

ボールが穴に消えた瞬間のルーレットの位置がそのまま結果。ただし「必ず解決する」ことは保証が要るので、一定時間を過ぎたら中心へ引く力を毎秒少しずつ強めている（安定軌道でゲームが止まらないための保険）

### チンチロ

トレイに投げた 3 個のサイコロの上面を読んで役を判定する。出目を先に決めてから見た目を合わせる、という作りにはしていない

### ダイス（ミニキューブ）

一辺 0.52 に対して横穴の開口が 0.46 しかないため、物理的に横穴を抜けられず必ず前面に到達する。不可視のガイドのような仕掛けは使っていない

## メダル収支をどう設計したか

払い出し率は約 90% です。数字を決め打ちしたのではなく、横穴（ハウスエッジ）から抜けるメダルの割合を専用テストで実測し、そこから逆算しました。実測値は 29.3% ± 1.9%（n=2331）で、これが payback = (1−s)(1+w) + jp の s にあたります。

この構造でいちばん効くのは横穴の寸法です。投入の (1−s) はどうやっても前面へ戻るので、s=29.3% なら盤面が 1 枚も払わなくても 71% は返ってしまう。盤面・ボウル・JP の 3 つは残り 20 ポイントを取り合っているだけ、という関係になります。

### 横穴の長さ・高さ ── 最強のレバー

ドレイン率 s そのものを動かす。ただし高さはミニキューブの一辺 0.52 未満が絶対条件で、超えるとダイスが横穴から抜けてすごろくが始まらなくなる

### medalsPerBall ── 強いレバー

1 手ぶんの「値段」。払う額はそのままで払う頻度だけ下がるので、1 回の当たりが大きくなる。25→40 にして 90% に着地させた

### 盤面の配当・ジャックポットの積立率 ── 弱いレバー

PAYOUT_SCALE を 0.50→0.30 に落としても払い出し率は 4 ポイントしか動かず、盤面がケチに見えるだけだった。積立率も jp 項にしか効かない

### 触ったら測り直す

メダルを大きく厚くした（r 0.30→0.32 / t 0.08→0.105）ときに s が 48%→24% まで落ち、払い出し率が 110% を超えて胴元が負けた。太いコインはテーパーに押されて壁から遠ざかるため。寸法を触ったら必ず排出率テストを回し直す

| 還元チャネル | 投入 1 枚あたり |
| --- | --- |
| 横穴を抜けずに前面へ戻る分（素通り） | 70.7% |
| 盤面・抽選ボウル・チンチロの払い出し | 9.2% |
| ジャックポット（長期平均） | 10.4% |
| 合計（払い出し率） | 90.2% |

*投入 1 枚が返ってくる内訳。いちばん上の素通り分は設計でどうにもできない下限で、残り 20 ポイントを 3 つのチャネルが取り合っている*

## アーキテクチャと性能

### 物理と描画の分離

Rapier の剛体が唯一の座標の持ち主で、three.js は毎フレームそれを転写するだけ。固定タイムステップ 60Hz の物理ループと可変レートの描画ループを分け、演出やチューニングが物理の再現性を壊さない構造に

### 描画コスト

全メダルを InstancedMesh 2 枚（通常 / 発光 JP）+ 剛体プールの再利用で管理。最大 500 枚が同時に転がっても枚数ぶんのメッシュは増えない

### 外部アセット完全ゼロ

メダルのギザ・リム・打刻はアルベド / バンプ / ラフネスの 3 枚が一致する形で Canvas 2D から生成し、効果音は Web Audio のオシレータ / ノイズ合成で作っている

### 寸法をハードコードしない

サイコロトレイとボウルの取り付け位置は layout.ts の wallMount(side, z) が台形形状から導出する。台形を切り直したときに手書きの座標だけ取り残されるのを防ぐため、x は書かない

## 非決定的な挙動をどう検証するか

物理抽選は結果が毎回変わるため、期待値の一致では検証できません。そこで `?debug` でデバッグ API を有効にし、状態機械の遷移を観測して「起動 → 投入 → 払い出し」「すごろく → idle 復帰」「すごろく → GOLD MINE → 抽選ボウル → チンチロ連鎖」が必ず解決することを Playwright + headless Chromium で確認する方式にしました。E2E は 8 本で、確率分布は 6 万回サンプル、払い出し率は横穴の排出率の実測から逆算しています。

ヘッドレス環境はソフトウェア GL なので描画が律速になり、実時間の 1/30 でしか物理が進みませんでした。1 フレームに物理とロジックだけを n ステップ余分に進めて描画しない turbo を入れ、10 分超かかっていたテストを十数秒にしています。1 ステップは固定 dt なのでシミュレーション結果は変わりません。

## 生成 AI の活用について

- 企画・ゲームデザイン（すごろく + 抽選ボウル + チンチロの連鎖構造、ダイスを横穴より大きくして前面へ届かせる仕掛け）と仕様の決定は自分
- 「抽選はスクリプト誘導ではなく実物理で」「トレイとボウルは壁に直付けにする」など、実機で遊んだ感覚に基づく指示を数十回のイテレーションで反復。初版のスロット + 円盤 + JPC を全面的に作り直す判断も自分
- AI には指示に基づく実装・E2E テスト作成・物理パラメータ調整の試行を担当させ、見た目・手触り・確率感の受け入れ判断は自分が行った
